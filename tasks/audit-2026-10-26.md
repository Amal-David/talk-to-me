Four independent reviewers covered auth and identity, relay correctness and MCP, the web surface and config, and docs, the CLI and supply chain. Findings below are de-duplicated. "Confirmed" means reproduced against Miniflare; proof scripts are in the session scratchpad (`audit-auth/`, `audit-relay/`, `audit-web/`, `audit-docs/`). **Bottom line:** no finding lets an outsider act as a peer, reach another group, read messages, or gain access without the owner's passkey. Five issues should be fixed before the first deploy, because the `workers.dev` address on Workers Free has no rate limiting in front of it.

## Fix before deploying

| # | Sev | Finding | Status | Fix |
| --- | --- | --- | --- | --- |
| 1 | Medium | Anyone can lock the owner out of `/owner/setup`: five wrong guesses make even the correct code return 429, and five more every 15 minutes keep it locked. Setup is first-time enrollment and the only recovery path. (`owner.ts` `checkSetupCode`) | Confirmed | Drop the global failure lockout; the code has 192+ bits, so guessing is not a threat. |
| 2 | Medium | Anonymous client registration plus `GET /authorize` shows every group, peer, route and topic, although `/v1` deliberately hides which groups exist. (`oauth.ts` GET `/authorize`, `owner-pages.ts` approval page) | Confirmed by two reviewers | Show the identity choices only after the owner's passkey assertion (or an owner session). |
| 3 | Medium | Client registration is open to anyone using a public allowlisted redirect (ChatGPT's, Grok's). Each `/register` and each `GET /authorize` writes to KV, so roughly 1,000 anonymous requests exhaust Workers Free's daily KV writes and break token issuance and refresh until the reset. `workers.dev` cannot rate-limit. | Confirmed (writes counted); quota effect inferred | Accept registration only during a short window the owner opens from the signed-in owner page ("connect a new host", for example 10 minutes). This also closes suspicion S1. |
| 4 | Medium | A wake held back while a group is paused is never sent after resume unless other traffic happens to reschedule the alarm; the request later expires with its wake `suppressed`. (`mailbox.ts` `control`, `alarm`, `schedule`) | Confirmed | Reschedule after `control()`; in the post-sync recheck, return a paused wake to `pending` instead of `suppressed`. |
| 5 | Low | A group or peer name containing `:` makes approval fail with 500 after the passkey challenge and consent are spent and a dangling live connection has been created (the OAuth library rejects `:` in `userId`). | Confirmed | Encode `userId` (hash of `group/peer`); create the connection only after `completeAuthorization` succeeds. |

| 6 | An OAuth app's self-reported name has no length limit and keeps bidirectional-override characters; a 600 KB name pushes the "not verified" notice far down the page, and a long name truncates the redirect host out of the Connections label. | Confirmed | Strip control and format characters, cap at about 60 characters, show the name quoted rather than as the heading, and put the host first in the label. |

## Docs that no longer match the code

- `docs/VERIFICATION.md` still records v0.1 (50 tests, 29 KiB, no runtime dependencies, undici 7.29.1).
- `SECURITY.md` says revoking a connection blocks queued wake dispatch; only disabling a peer does.
- `docs/OPERATIONS.md` recommends a rate-limit rule for `/owner/*`, which is unavailable on `workers.dev`; it has no deploy section (KV namespace, `workers_dev`, which values are vars versus secrets, the two-deploy order) and does not state the Workers Free caps.
- `docs/API.md`: a garbled connection-token sentence; "irreversible revocation" in the verification list; `/mcp` also needs a valid `RELAY_PUBLIC_URL` and redirect allowlist.
- `docs/ARCHITECTURE.md` still says the transaction rechecks the token deadline and lists MCP as future work; `docs/INTEGRATIONS.md` still calls CLI polling the supported baseline.
- `README.md` implies the owner and OAuth flows run under `npm run dev`; they cannot, because the relay URL must be public HTTPS.
- Groups are described as private, but the policy is shown on the approval page (see #2).

## Unverified suspicions

- **S1 consent phishing:** an attacker connects the relay from their own ChatGPT account and sends the owner the `/authorize` link; the page looks identical to a real request. Whether it works depends on ChatGPT's callback checking the browser session. Fix #3 removes it either way.
- **CPU on Workers Free:** passkey verification, OAuth crypto and building the MCP server may exceed 10 ms per request (error 1102). Measurable only after deploying.
- **Durable Object row writes:** anonymous sign-in-challenge and token-lookup floods write to the single Owner object; under the Free plan's daily row-write quota a sustained flood could take the relay down for the day.
